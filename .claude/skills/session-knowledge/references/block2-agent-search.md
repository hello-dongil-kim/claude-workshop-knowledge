# Block 2: 에이전트 검색 — 질의확장 → grep → 읽기 → 추론

> 🎛️ **지휘자 원칙:** 명령을 직접 칠 필요 없습니다. **Claude에게 검색을 시키고** 결과를 판정하세요.

## EXPLAIN

이번이 기본 트랙의 심장이다. **임베딩·색인·파이썬 없이**, Claude Code만으로 의미 검색에 근접한다.

### 단순 grep과 무엇이 다른가

> 💡 **grep이 뭐냐면** — 폴더 전체에서 글자를 그대로 찾는 "통합 Ctrl+F"다. Claude Code가 파일을 찾는 기본기. 단, 글자 그대로라 "집값"으로는 "부동산" 노트를 못 찾는다.

혼자 grep을 치면 "집값"만 찾는다. **에이전트 검색**은 Claude가 사서처럼 4단계를 돈다 — **AI가 Ctrl+F로 후보를 찾고 → 직접 열어 읽고 → 질문에 맞는 순으로 추려준다**:

```text
① 질의 확장   "집값" → "집값 OR 부동산 OR 전세 OR 주거 OR 매매"
② grep/glob   확장한 단어들 + frontmatter 필터로 후보 폭넓게 수집
③ 읽기        후보 노트의 본문·frontmatter를 실제로 읽음
④ 추론 랭킹   질문 의도에 맞는 순으로 Claude가 다시 정렬 → 상위 N개
```

→ 단어가 달라도(①), 구조 신호로 좁히고(②), 진짜 내용을 보고(③), 의도로 줄 세운다(④). 임베딩이 하던 "의미 매칭"을 **Claude의 언어 이해가 대신**한다.

### 왜 이게 통하나

- Claude는 동의어·맥락을 안다 → 질의 확장이 임베딩의 "유사어 리콜"을 흉내
- Claude는 후보를 직접 읽고 판단 → 단순 점수보다 **의도 적합도**가 높을 때가 많음
- 색인이 없어 **항상 최신**(새 노트도 바로 검색됨) — 갱신 단계가 필요 없다

### 한계 — 그리고 "언제 벡터(B8)로 가나"

에이전트 검색이 막히는 두 순간이 곧 심화(B8) 벡터 RAG가 필요한 신호다.

- **어휘가 너무 멀 때**: 질의 확장으로도 안 닿는 경우가 있다. 예) "사과" 검색 → "애플(기업)" 노트, 혹은 영문 전문용어가 한글 약어로만 적힌 노트. 임베딩(의미 벡터)은 이런 먼 의미 연결을 더 잘 잡는다.
- **규모가 클 때**: 후보가 수백을 크게 넘으면 Claude가 다 못 읽는다(매번 재검색이라 느려짐). B1 구조(필터·MOC)로 좁히는 게 먼저지만, 한계가 있다.

**현실 기준 (대략):**

| 내 Vault 규모 | 권장 |
|---|---|
| ~수백 개 | **에이전트 검색으로 충분** (B0~B5) |
| 수천 개 | 에이전트 + 강한 필터/MOC, 또는 벡터 고려 |
| 수만+ / 매번 고속 시맨틱 | **벡터 RAG (B8)** |

> 즉 "기본이 충분한데 왜 B8?"의 답: **위 두 한계를 실제로 만났을 때**. 안 만났으면 기본으로 끝내도 된다.

### 반복 가능하게 — "검색 스킬"로

매번 4단계를 설명하기 번거로우니, 이 방식을 **Vault 검색 스킬**로 굳힌다. `templates/vault-search-skill/`을 Vault에 두면 "지식 검색해줘: 질문"으로 호출 → Claude가 질의확장→grep→읽기→추론을 자동 수행.

## EXECUTE

**Step 1: 손으로 한 번 — 에이전트 검색을 Claude에게 시키기**
- "내 Vault에서 '○○' 관련 노트를 찾아줘. **먼저 동의어로 검색어를 넓히고**, frontmatter로 좁히고, 후보를 읽어본 뒤, 내 질문에 맞는 순으로 상위 5개를 근거와 함께 보여줘."
- 단순 grep 대비 더 적절한 노트가 위로 오는지 관찰.

**Step 2: 검색 스킬 설치**
- `templates/vault-search-skill/`를 Vault(또는 `.claude/skills/`)에 복사하게 시키고, 내 Vault 경로·구조에 맞게 다듬어줘.

**Step 3: 스킬로 호출**
- "지식 검색: ○○" 식으로 불러 결과 확인.

> ✅ **이렇게 되면 성공:** 단어를 직접 안 쓴 질문(예: 글엔 "구별짓기", 내 질문은 "취향이 계급")에도 관련 노트가 상위에 뜨면 성공 — Claude가 의미로 찾고 있는 것이다.

## QUIZ

**문제:** 에이전트 검색이 단순 grep보다 의미를 잘 잡는 핵심 이유는?

| 선택지 | 내용 |
|--------|------|
| A | Claude가 질의를 동의어로 넓히고, 후보를 읽어 의도로 다시 랭킹하기 때문 |
| B | grep을 더 빠르게 실행하기 때문 |
| C | 노트를 미리 벡터로 색인해두기 때문 |

**정답:** A — 질의 확장 + 읽기 + 추론 랭킹이 단어 불일치를 메운다. B는 속도와 무관하고, C는 색인을 쓰는 벡터(심화 B8) 방식이라 "임베딩 없는 에이전트 검색"의 설명으로 틀렸다.

**적용 문제 (시나리오):** 에이전트 검색을 돌렸더니 후보가 800개나 잡혀 Claude가 다 못 읽고 품질이 떨어진다. 가장 적절한 대응은?

| 선택지 | 내용 |
|--------|------|
| A | frontmatter 필터(type·tags·기간)와 MOC로 후보를 먼저 좁힌 뒤 검색한다 |
| B | 질의 확장을 끄고 단어 하나로만 grep한다 |
| C | 무조건 벡터 RAG로 갈아탄다 |

**정답:** A — 후보가 많으면 B1의 구조 신호(frontmatter 필터·MOC 경유)로 범위를 줄이는 게 먼저다. B는 의미 리콜을 버려 오히려 못 찾고, C는 유효한 옵션이나 수백 규모에선 과하다(벡터는 수천+·고속 반복일 때).
