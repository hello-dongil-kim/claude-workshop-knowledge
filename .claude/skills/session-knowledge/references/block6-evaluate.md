# Block 6: (선택) 자가평가 — 다관점으로 깎기

## EXPLAIN

> **전제:** B0~B5 완료(작동하는 검색 엔진). 이 블록은 "만들고 끝"이 아니라 "더 낫게"의 캡스톤이다.

### 왜 자가평가인가

내가 만든 시스템은 내 눈엔 잘 보이는 약점이 안 보인다. **여러 관점으로 일부러 깎아보면** 빠진 곳이 드러난다. 거창한 도구 없이 **Claude에게 다관점 점검을 시키는 것**만으로 충분하다.

### 5개 관점 (체크 축)

| 축 | 묻는 것 |
|----|---------|
| 아키텍처 | 구조가 견고한가? 원본/인덱스 분리, 경로 선택이 맞나 |
| 검색 품질 | 실제로 잘 찾나? 못 찾는 질문 유형은? |
| 운영 | 갱신이 지속 가능한가? 빠뜨리기 쉬운 건? |
| 리스크 | 데이터 유실·키 노출·고아 청크 가능성은? |
| 비용 | 과한 곳은? 줄일 여지는? |

### 핵심 — 사람 승인 게이트

AI의 점검 결과를 **그대로 자동 반영하지 않는다.** 제안을 받고 **내가 한 개를 골라** 적용한다. "AI가 OK하면 끝"이 아니라 사람이 최종 결정 — 품질의 마지막 보루다.

### 다관점이 단일 의견보다 나은 이유

한 관점만 보면 그 관점의 편향에 갇힌다. 아키텍처만 보면 검색 체감을 놓치고, 비용만 보면 품질을 놓친다. 축을 나눠 보면 **충돌·사각지대**가 드러난다 — 그게 개선 후보다.

> (도구를 더 쓰고 싶으면: 여러 모델에게 같은 걸 묻고 합의/이견을 비교하는 방식도 있다. 하지만 비개발자는 Claude 단일 다관점으로 시작하면 충분하다.)

## EXECUTE

**Step 1: Claude에게 다관점 점검 요청**
- 예시 프롬프트:
  > "내가 만든 vault 검색 시스템(구조화 + 에이전트 검색 + MOC; 심화 트랙이면 벡터 RAG 포함)을 아키텍처·검색품질·운영·리스크·비용 5개 관점으로 평가하고, 각 관점의 약점 1개와 개선안 1개를 제시해줘. 점수도 매겨줘." (※ 기본 트랙은 비용 0이라 '비용' 축은 심화에만 해당)

**Step 2: 실제로 못 찾는 질문 찾기**
- 일부러 어려운 질문 3~5개를 검색해본다. 엉뚱하게 나오는 게 있으면 → 그게 개선 후보(청킹? 하이브리드? 필터?).

**Step 3: 한 개만 골라 적용 (사람 게이트)**
- 제안 중 **임팩트 대비 노력**이 좋은 것 1개를 골라 Claude와 함께 반영. 나머지는 메모만.

> ✅ **이렇게 되면 성공:** 5개 관점 평가에서 **내 시스템의 약점 1개**를 구체적으로 집어내고, **개선안 1개를 골라** (적용 또는 메모) 하면 성공 — 시스템이 "완성"에서 "진화"로 넘어간다.

## QUIZ

**문제:** 자가평가에서 "사람 승인 게이트"가 중요한 이유는?

| 선택지 | 내용 |
|--------|------|
| A | AI 제안을 자동으로 다 반영해야 빠르기 때문 |
| B | AI 점검을 그대로 자동 적용하면 품질이 무너질 수 있어, 사람이 골라 반영해야 하기 때문 |
| C | 사람은 평가에 참여하면 안 되기 때문 |

**정답:** B — AI의 점검은 후보일 뿐, 검증 없이 자동 반영하면 엉뚱한 변경이 쌓인다. 사람이 최종으로 골라 적용하는 게 품질의 보루다. A는 정반대(자동 전면 반영은 위험), C는 사람을 배제하자는 틀린 말이다.

---

**적용 문제 (시나리오):** Claude가 5개 관점 점검에서 개선안 6개를 내놨다. 비개발자인 내가 가장 현명한 다음 행동은?

| 선택지 | 내용 |
|--------|------|
| A | 6개를 전부 한 번에 Claude에게 자동 반영시킨다 |
| B | 임팩트 대비 노력이 좋은 1개를 골라 적용하고, 나머지는 메모로 남긴다 |
| C | 평가가 6개나 나왔으니 시스템을 처음부터 다시 만든다 |

**정답:** B — 작은 개선 1개를 골라 검증하며 반영하는 "작은 루프"가 안전하고 누적된다(사람 게이트). A는 검증 없는 전면 변경이라 위험하고, C는 멀쩡한 시스템을 버리는 과잉 대응이다.
