# Block 0: 누적의 벽 — 왜 검색 체계가 필요한가

## EXPLAIN

### 1편을 잘 따랐다면 생기는 문제

session-obsidian(1편)을 따라 했다면 지금 Vault에는 클리핑·정리노트가 **수백~수천 개** 쌓였을 것이다. 좋은 일이다. 그런데 역설이 생긴다.

> **쌓을수록 못 찾는다.**

노트가 30개일 땐 눈으로 훑어 찾는다. 3,000개가 되면? 제목도 기억 안 나고, 폴더 어디 뒀는지도 모른다. 사람도 AI도 매번 "찾기 비용"을 다시 낸다 — 1편 Block 0에서 본 문제가 이번엔 **내 Vault 안에서** 재발한다.

### grep(키워드 검색)의 한계

Claude가 Vault에서 자료를 찾는 기본기는 **grep**(글자 일치)이다. 문제는:

- "취향이 계급이 되는 과정" 노트를 찾는데, 그 노트엔 "계급" 대신 "구별짓기"라고 적혀 있다 → grep 실패
- "집값" 검색 → "부동산·주거·전세" 노트는 안 잡힘
- 한국어는 조사·어미 변형이 많아 글자 일치가 더 빗나간다

**사람은 의미로 기억하는데, grep은 글자로만 찾는다.** 이 간극이 누적의 벽이다.

### 해법 두 가지 — 그리고 이 세션의 선택

의미로 찾게 하는 길은 두 가지다.

| 길 | 방식 | 이 세션 |
|---|---|---|
| **에이전트 검색** | Claude가 **질의를 넓혀(동의어) → grep → 읽고 → 추론으로 랭킹** | **기본 트랙 (B1~B5)** — 설치·키·비용 0 |
| **벡터 검색** | 노트를 임베딩(의미 벡터)해 색인, 최근접 검색 | **심화 트랙 (B8, 선택)** — 임베딩 모델 필요 |

> 핵심 결정: **기본은 "Claude를 사서로" 쓴다.** 임베딩·파이썬·API 키 없이, Claude Code의 grep·읽기·추론만으로 의미 검색에 가깝게 간다. 대부분의 개인 Vault엔 이걸로 충분하다. 진짜 대규모·고속이 필요하면 그때 벡터(B8).

### 1편(라이트타임)과의 관계

1편은 "자료가 들어올 때 정리"(클리핑→정리노트)를 손에 익혔다. 이번 2편은 **"질문할 때 의미로 찾기"(쿼리타임)** 를 붙인다. 둘이 합쳐져야 "쓸수록 똑똑해지는" 두 번째 뇌가 완성된다.

### 이 세션이 만들 것 (기본 트랙 미리보기)

```text
[내 Vault]
   │  ① 검색 잘 되는 구조 (index·frontmatter schema·MOC)   ← B1
   ▼
[구조화된 Vault]
   │  ② 에이전트 검색 스킬 (질의확장→grep→읽기→추론)        ← B2~B3
   ▼
"집값" 물어보면 → Claude가 "주거·전세" 노트까지 의미로 찾아줌
   │  ③ 주제 지도(MOC) — Claude가 묶음                      ← B4
   ▼
[지식 지도] + ④ 갱신·점검 운영                              ← B5
   (선택) ⑤ 벡터 색인으로 대규모·고속 업그레이드            ← B8
```

원칙: **원본 노트가 진실의 원천.** 기본 트랙은 아예 별도 색인도 안 만든다(매번 신선). 심화의 벡터 색인도 언제든 재생성 가능한 캐시.

### 역할 분담

- **사람:** 무엇을 쌓을지 + 좋은 질문
- **Claude:** 질의 확장·검색·읽기·랭킹·정리 — 직접 칠 필요 없이 시킨다

### 🧠 핵심 원리 6 (이 세션을 관통 — 단계 너머로 추론하는 데 쓴다)

세부 명령은 잊어도, 이 원리만 쥐면 내 상황에 맞게 스스로 변형할 수 있다.

1. **원본 = 진실의 원천, 색인 = 캐시.** 노트는 불변, 검색 구조물(인덱스·벡터)은 언제든 재생성. 망가져도 안전.
2. **구조가 검색 품질의 절반.** 임베딩 이전에 index·frontmatter·MOC. AI는 폴더 깊이보다 메타데이터·링크·지도를 읽는다.
3. **의미 검색은 두 길.** 에이전트 검색(Claude 추론, 무설치) / 벡터(임베딩, 대규모). **규모로 고른다** — 정답은 하나가 아니다.
4. **사람 뷰 · 에이전트 뷰는 짝.** 사람은 눈으로 훑고(Obsidian·플러그인), 에이전트는 시켜서 찾는다(스킬). 경쟁 아님.
5. **무설치·키리스 우선.** 되도록 키·비용 없이. 로컬·에이전트 먼저, 외부 API는 정말 필요할 때.
6. **항상 최신을 의식.** 에이전트 검색은 색인이 없어 자동 최신. 벡터는 갱신해야 최신. 무엇을 쓰든 "검색이 보는 상태"를 알아야 한다.

설치 전 워밍업. 직접 떠올려보세요:

**Step 1: 내 Vault는 지금 몇 개인가요?**
- 대략 감만. 30개 vs 3,000개 — "눈으로 훑어 찾기"가 아직 되나요?

**Step 2: 최근 "분명 정리해뒀는데 못 찾은" 경험이 있나요?**
- 그때 어떤 단어로 찾았나요? 노트엔 다른 단어로 적혀 있지 않았나요? → grep이 놓치고 의미 검색이 잡을 자리.

**Step 3: 어느 트랙으로 시작할지 감 잡기**
- 기본(Claude only, 무설치)으로 충분할지, 아니면 노트가 수천이라 처음부터 벡터(B8)가 필요할지.

> ✅ **이렇게 되면 성공:** "내 Vault가 grep으로 찾기 버거운 규모"임을 체감하고, "의미로는 아는데 글자로는 못 찾은" 사례 1개를 댈 수 있으면 성공 — 그게 이 세션이 풀 문제다.

## QUIZ

**문제:** 수천 개로 쌓였을 때 grep(키워드 검색)의 가장 큰 약점은?

| 선택지 | 내용 |
|--------|------|
| A | 노트가 많아지면 grep이 실행조차 안 된다 |
| B | 같은 의미라도 다른 단어(집값↔주거)면 못 찾는다 |
| C | grep은 한국어를 지원하지 않는다 |

**정답:** B — grep은 글자 일치만 보므로 의미로 기억한 걸 다른 단어로 적어두면 놓친다. 이게 의미 검색이 필요한 이유다. A는 틀림(많아도 동작은 함, 의미를 못 잡을 뿐), C도 틀림(한국어 글자도 찾음 — 못 잡는 건 "의미").

**적용 문제 (시나리오):** 클리핑 2,000개가 쌓였는데, 설치·API 키 없이 **지금 당장** 의미 기반으로 찾고 싶다. 가장 적절한 출발은?

| 선택지 | 내용 |
|--------|------|
| A | 폴더를 주제별로 더 잘게 나눠 다음부터 찾기 쉽게 한다 |
| B | Claude에게 질의를 넓혀(동의어) grep·읽기·추론으로 찾게 하는 에이전트 검색부터 쓴다 |
| C | 반드시 임베딩 벡터 DB를 먼저 구축해야만 한다 |

**정답:** B — 기본 트랙(에이전트 검색)은 설치·키 없이 Claude의 질의확장+grep+추론으로 의미 검색에 근접한다. 무설치로 바로 가능. A는 AI가 깊은 폴더를 잘 안 뒤지고 과거 2,000개는 그대로 못 찾는다. C는 벡터가 강력하나 임베딩 모델·설치가 필요한 심화 선택지로, "지금 당장 무설치"엔 과한 전제다.
